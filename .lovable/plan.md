

# Migrate to Your Own Supabase Account

This plan covers everything required to disconnect from Lovable Cloud's managed Supabase instance and point the app at a Supabase project in your own account.

## Important Note Up Front

Lovable Cloud cannot be "disabled" on a project once enabled — the auto-generated files (`src/integrations/supabase/client.ts`, `client.server.ts`, `auth-middleware.ts`, `types.ts`, `.env`) are managed by the platform and will keep regenerating against the Lovable-managed project ref `fxokholudswvvsnxugaj`.

To truly use **your own** Supabase account, you have two realistic paths:

1. **Recommended**: Create a fresh Lovable project **without** Lovable Cloud, then connect it to your own Supabase via the native Supabase integration. Migrate the schema + code over.
2. **Workaround in this project**: Override the managed clients with hand-written ones that read from your own env vars. Fragile — Lovable may regenerate the managed files on future edits.

The rest of this plan assumes **path 2** since you asked what changes in *this* project. If you want path 1 instead, say so and I'll write a different plan.

## What Changes

### 1. Supabase project setup (in your own account)
- Create a new project at supabase.com → grab `Project URL`, `anon/publishable key`, `service_role key`.
- Recreate the full schema by running every file in `supabase/migrations/` (in timestamp order) against your new database via the Supabase SQL editor.
- Recreate the 6 database functions: `handle_new_user`, `set_updated_at`, `request_borrow`, `respond_to_request`, `confirm_handover`, `confirm_return`.
- Recreate the `on_auth_user_created` trigger that calls `handle_new_user` (in `auth.users`).
- Recreate the `transaction_status` enum and any other custom types.
- Re-enable RLS on all tables (`books`, `profiles`, `transactions`, `posts`, `post_likes`, `post_comments`) and recreate every policy listed in the schema context.
- Configure Auth providers (email/password, optionally Google) and set the Site URL + redirect URLs to match your dev/preview/published domains.

### 2. Environment variables
- Replace the values in `.env` with your own project's URL + keys. Note: `.env` is normally auto-managed by Lovable Cloud — you may need to either disconnect Cloud or accept that values can be overwritten.
- Update Lovable runtime secrets via the secrets tool: `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_DB_URL`.

### 3. Code files to overwrite
Three "auto-generated" files currently point at the managed project. They need to be replaced with hand-written versions that read from your env vars:

- `src/integrations/supabase/client.ts` — browser client
- `src/integrations/supabase/client.server.ts` — admin client (service role)
- `src/integrations/supabase/auth-middleware.ts` — server function auth middleware
- `src/integrations/supabase/types.ts` — regenerate from your own project using the Supabase CLI (`supabase gen types typescript`)

The `// This file is automatically generated. Do not edit it directly.` header on these files needs to be removed; otherwise the platform may overwrite them.

### 4. Things that do NOT need code changes
- All app code that imports `@/integrations/supabase/client` keeps working unchanged (`src/routes/*.tsx`, `src/components/Feed.tsx`, `src/hooks/use-credits.ts`, `src/lib/auth.tsx`, etc.).
- RPC names, table names, and column shapes stay identical because you're recreating the same schema.

### 5. Data migration (optional)
- If you want existing users/books/posts/transactions in the new project, export from the Lovable-managed DB (`pg_dump` via `SUPABASE_DB_URL`) and restore into your new project. Otherwise you start with an empty database and users must re-sign-up.

### 6. External integrations to reconfigure in your Supabase dashboard
- Email templates (signup confirmation, password reset).
- Google OAuth credentials, if you use Google sign-in.
- Any `pg_cron` jobs or webhooks (none exist today, but worth noting).
- Storage buckets (none exist today).

## Risks

- **Regeneration risk**: Because Lovable Cloud is enabled on this project, the platform may overwrite your hand-edited `client.ts`, `client.server.ts`, `auth-middleware.ts`, and `.env` whenever Cloud-related actions run. Path 1 (new project, no Cloud) avoids this entirely.
- **Type drift**: `types.ts` must be regenerated against your new schema each time you change tables; the Lovable auto-regen no longer applies.
- **Auth sessions**: All currently logged-in users will be signed out and must re-register unless you migrate the `auth.users` table data.
